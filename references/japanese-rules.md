# 日本語向け変換規則

## 1. 結論を早める

悪い例:

> これまでの経緯や複数の観点を総合的に勘案すると、必ずしも一概には言えないものの、現時点ではA案が比較的妥当であると考えられます。

改善例:

> 現時点ではA案を推奨します。  
> ただし、条件XではB案が適します。

真の不確実性は残し、回りくどい導入だけを削る。

## 2. 括弧へ重要情報を入れない

悪い例:

> 本番反映は金曜日です（ただし、監査承認が木曜日までに得られない場合は延期します）。

改善例:

> 本番反映は金曜日です。  
> 監査承認を木曜日までに得られない場合は延期します。

括弧内の条件が意思決定に影響するため、本文へ昇格する。

## 3. 定義を二文に分ける

悪い例:

> RPO（障害発生時にどこまでのデータ損失を許容するかを示す目標値）を決めます。

改善例:

> RPOを決めます。  
> RPOは、障害発生時に許容するデータ損失の範囲です。

略語を初回だけ示す必要がある場合:

> 正式名は Recovery Point Objective です。以下、RPOと呼びます。

## 4. 主体を明示する

悪い例:

> 確認後に反映し、問題があれば戻します。

改善例:

> 運用担当者が変更内容を確認します。  
> 開発担当者が本番へ反映します。  
> 問題が発生した場合、運用担当者が直前版へ戻します。

主体が不明な場合は推測しない。

> 変更内容の確認担当者を決める必要があります。

## 5. 指示語を具体名へ戻す

悪い例:

> これを修正すると、それにも影響します。

改善例:

> 認証ミドルウェアを修正すると、管理画面のログイン処理にも影響します。

## 6. 一つの概念に一つの名称を使う

悪い例:

> 利用者はアカウントを作成します。その後、ユーザーは会員情報を更新します。

改善例:

> ユーザーはアカウントを作成します。  
> その後、ユーザーは登録情報を更新します。

文体上の変化のためだけに同義語を切り替えない。

## 7. 条件、例外、注意を分ける

推奨構造:

```text
結論: A案を採用します。

条件:
- 監査承認を木曜日までに得ること

例外:
- 承認が遅れた場合は翌週へ延期します

注意:
- データ移行後は旧形式へ直接戻せません
```

重要度の低い短文では、すべてを見出し化しない。

## 8. 箇条書きを使い過ぎない

箇条書きが適する場面:

- 三つ以上の並列項目
- 操作手順
- 比較軸
- 条件や例外
- チェック項目

段落が適する場面:

- 因果関係を説明する
- 一つの論証を展開する
- 語調や物語性が重要
- 項目同士が独立していない

## 9. 不確実性を正確にする

悪い削減:

> この変更で性能が改善します。

原文が「改善する可能性がある」なら断定しない。

改善例:

> この変更で性能が改善する可能性があります。  
> 効果はベンチマークで確認します。

曖昧さを減らせる場合:

> 多くの場合、改善する可能性があります。

より明確に:

> 検証した10ケース中8ケースで処理時間が短くなりました。未検証の環境では効果を断定できません。

## 10. ソースコードと自然文を分離する

コマンドやコードを文中へ埋め込まない。

悪い例:

> `npm test`（失敗した場合は `npm test -- --runInBand`）を実行します。

改善例:

> まず、次を実行します。

```bash
npm test
```

失敗した場合は、次を実行します。

```bash
npm test -- --runInBand
```

## 11. コードの参照情報を番号でまとめる

根拠として添えられた長いファイルパスや行番号は、末尾の「参照」へ移せる。
括弧で囲まれた参照にも、文中へ直接置かれた参照にも使う。

- 本文では、対応する主張の句点の直前に `[1]` のような短い番号を置く
- 新しい番号は初出順に付ける。同じ参照先を再び使うときは同じ番号を使う
- 同じファイルでも行範囲やリビジョンが異なる参照には別の番号を付ける
- 一つの主張が複数の参照先を持つ場合は、`[1][2]` のように対応する番号を並べる
- 末尾には `- [1] 参照先` の形式で一覧を置く。既存のリンクはリンク先を保って移す
- 原文にあるパス、行範囲、URL、リビジョンを保持し、不明な情報を補わない
- 既存の参照番号や脚注と衝突させない。指定された引用形式がある場合は、その形式を保つ

コード中の配列添字など、参照番号以外の角括弧は変更しない。
修正手順で開くファイル名や、判断に必要な条件・警告は手順の近くに残す。

変換後は、本文の各番号に参照先があり、参照一覧の各項目が本文から参照されていることを確認する。
具体例は `../examples/before-after.md` の例6・例7を参照する。

## 12. 長い段落を文脈に合わせて改行する

段落が長く、読み進めた位置や必要な情報を見つけにくいときは、文の役割を見て区切る。
表示幅や文字サイズが分かる場合は、表示された段落の大きさも確認する。
表示条件が不明な場合は、固定の表示行数を仮定せず、意味のまとまりを基準にする。

まず、各文が結論、理由、具体例、条件、次の行動のどれを担うかを確認する。
同じ論点を説明する文をまとめ、読み手が一つの情報を受け取って次へ進める句点を改行候補にする。
接続詞の有無だけで改行位置を決めない。

| 文脈 | 改行の判断 |
|---|---|
| 結論を説明し終え、詳しい理由や具体例へ進む | 段落が長い場合は、説明のまとまりの境界で改行する |
| 状況説明が終わり、読み手の行動へ進む | 空行で段落を分け、行動を見つけやすくする |
| 次の文が、直前の主張の重要な条件・例外を示す | 同じまとまりに置き、条件を読まずに判断する配置を避ける |
| 次の文が「そのため」「この設定」などで直前を受ける | 因果関係や参照先が明確な位置に保つ。離れすぎる場合は区切る位置を変える |
| 数文で一つの論点が簡潔にまとまっている | そのまま保つ |

Markdownで同じ段落内に表示上の改行を入れる場合は、句点のあとに半角スペース2個と改行を置くなど、出力先が対応する記法を使う。
新しい段落にする場合は空行を置く。リスト内では項目の字下げを維持し、コードや引用の内部は変更しない。
参照番号は対応する主張と同じ文に保つ。

改行後は、細切れの文が連続していないか、条件や理由のつながりが追えるかを読み直す。
プレビューできる場合はWeb上の表示でも確認する。ソースの改行数やリントの指摘減少だけで読みやすさを判断しない。
