# 日本語向け変換規則

## 1. 結論を早める

悪い例:

> これまでの経緯や複数の観点を総合的に勘案すると、必ずしも一概には言えないものの、現時点ではA案が比較的妥当であると考えられます。

改善例:

> 現時点ではA案を推奨します。  
> ただし、条件XではB案が適します。

真の不確実性は残し、回りくどい導入だけを削る。

## 2. 括弧へ重要情報を入れない

悪い例:

> 本番反映は金曜日です（ただし、監査承認が木曜日までに得られない場合は延期します）。

改善例:

> 本番反映は金曜日です。  
> 監査承認を木曜日までに得られない場合は延期します。

括弧内の条件が意思決定に影響するため、本文へ昇格する。

## 3. 定義を二文に分ける

悪い例:

> RPO（障害発生時にどこまでのデータ損失を許容するかを示す目標値）を決めます。

改善例:

> RPOを決めます。  
> RPOは、障害発生時に許容するデータ損失の範囲です。

略語を初回だけ示す必要がある場合:

> 正式名は Recovery Point Objective です。以下、RPOと呼びます。

## 4. 主体を明示する

悪い例:

> 確認後に反映し、問題があれば戻します。

改善例:

> 運用担当者が変更内容を確認します。  
> 開発担当者が本番へ反映します。  
> 問題が発生した場合、運用担当者が直前版へ戻します。

主体が不明な場合は推測しない。

> 変更内容の確認担当者を決める必要があります。

## 5. 指示語を具体名へ戻す

悪い例:

> これを修正すると、それにも影響します。

改善例:

> 認証ミドルウェアを修正すると、管理画面のログイン処理にも影響します。

## 6. 一つの概念に一つの名称を使う

悪い例:

> 利用者はアカウントを作成します。その後、ユーザーは会員情報を更新します。

改善例:

> ユーザーはアカウントを作成します。  
> その後、ユーザーは登録情報を更新します。

文体上の変化のためだけに同義語を切り替えない。

## 7. 条件、例外、注意を分ける

推奨構造:

```text
結論: A案を採用します。

条件:
- 監査承認を木曜日までに得ること

例外:
- 承認が遅れた場合は翌週へ延期します

注意:
- データ移行後は旧形式へ直接戻せません
```

重要度の低い短文では、すべてを見出し化しない。

## 8. 箇条書きを使い過ぎない

箇条書きが適する場面:

- 三つ以上の並列項目
- 操作手順
- 比較軸
- 条件や例外
- チェック項目

段落が適する場面:

- 因果関係を説明する
- 一つの論証を展開する
- 語調や物語性が重要
- 項目同士が独立していない

## 9. 不確実性を正確にする

悪い削減:

> この変更で性能が改善します。

原文が「改善する可能性がある」なら断定しない。

改善例:

> この変更で性能が改善する可能性があります。  
> 効果はベンチマークで確認します。

曖昧さを減らせる場合:

> 多くの場合、改善する可能性があります。

より明確に:

> 検証した10ケース中8ケースで処理時間が短くなりました。未検証の環境では効果を断定できません。

## 10. ソースコードと自然文を分離する

コマンドやコードを文中へ埋め込まない。

悪い例:

> `npm test`（失敗した場合は `npm test -- --runInBand`）を実行します。

改善例:

> まず、次を実行します。

```bash
npm test
```

失敗した場合は、次を実行します。

```bash
npm test -- --runInBand
```
